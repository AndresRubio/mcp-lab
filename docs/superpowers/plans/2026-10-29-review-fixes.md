# Review fixes (2026-10-29) Implementation Plan

A whole-repository review on 2026-10-29 compared the code with the design spec, the milestone notes
and good practice. Every finding below was verified with a command or a scratch test. This plan fixes
them in three tasks. Tasks 1 and 2 touch disjoint files and run in parallel; Task 3 runs after both
have merged, because it edits every test file.

## Global Constraints

- Start from commit `71d9f00` (`main` after PR #6). Task 3 starts from the integration branch
  `fix/review-2026-10-29` once Tasks 1 and 2 are merged into it.
- Git identity: `AndresRubio <2109109+AndresRubio@users.noreply.github.com>`. No co-author or
  "generated by" trailers in commit messages.
- `./scripts/check.sh` must be green before the task is reported done: ruff, ruff format, pyright

  `isinstance` check first.

### Task 1: Gateway: a removed server exposes nothing, the audit sees stale entries, owners are required, dependencies are declared

Findings this task fixes, each with how it was shown:

1. A server removed from the registry still serves its resources and prompts.
   `docs/notes/m2a.md` line 28 says: "A server removed from the YAML exposes nothing until the
   restart that unmounts it." A scratch test deleted `opsdesk` from the YAML, reloaded, and found
   `tools/list` empty while `resources/templates/list` still listed `runbook://{service}`,
   `resources/read runbook://api` returned the runbook, `prompts/list` listed `postmortem`, and
   `prompts/get postmortem` returned the full prompt. The backing test,
   `test_server_removed_from_registry_exposes_nothing_until_restart` in
   `packages/mcp-gateway/tests/test_gateway.py`, asserts on tools only.

   Fix, preferred: make the sentence true. In `gateway/visibility.py`, when the server has no entry
   in `holder.current.servers`, hide resources, resource templates and prompts as well as tools, so
   that reads and `prompts/get` fail the way they do for a resource or prompt that does not exist.
   Use the FastMCP 4.1 `Transform` hooks for resources, templates and prompts (check
   `fastmcp.server.transforms.Transform` for the exact hook names; `list_tools` and `get_tool` are
   the model). For a server that is still listed, resources and prompts stay ungoverned, as the
   "governs tools only" gap says. Extend the existing test to assert templates, reads, prompt
   listing and `prompts/get` all fail or come back empty once the server is removed, and that they
   work again when the server is restored.

   Fix, fallback: if the `Transform` API has no hooks for resources or prompts in fastmcp 4.1.0,
   narrow the sentence in `docs/notes/m2a.md` to tools, add a characterization test that pins the
   current behaviour (resources and prompts of a removed server are still served), and list it under
   "Known gaps". Say in the report which route you took and why.

2. The audit cannot catch a tool that starts switched on. The design spec says: "New tools
   start switched off, and turning one on is a reviewed config change." `gateway/__main__.py` line
   50 computes `pending = [tool for tool in offered if tool not in entry.tools]`, so it only reports
   backend tools the registry lacks. A registry entry the backend does not offer (a stale name, a
   typo such as `List_Incidents`, or a tool listed before it ships) is accepted silently, and if it
   says `enabled: true` the tool is live the moment a backend ships it under that name.

   Fix: in `audit`, also report, per server, the listed tools the backend does not offer, as a
   separate line such as `<label>: listed but not offered: a, b`. Make `audit` exit with status 1
   when any such entry is enabled (a disabled stale entry is a cleanup item, an enabled one is a
   tool that would go live unreviewed); the `serve` command is unaffected. Keep the existing lines
   and their wording for the covered cases. Tests in `packages/mcp-gateway/tests/test_cli.py`: a
   stale disabled entry is reported and exits 0; a stale enabled entry is reported and exits 1; the
   demo registry still prints exactly what the README shows and exits 0. Update
   `docs/notes/m2a.md` ("Control plane and data plane" and "Disabled by default") to describe the
   new line and the exit status, naming the tests.

3. `owner` is optional on a tool. The spec says the registry lists tools "with owner and on/off
   state", and `ToolPolicy.owner` in `gateway/registry.py` is `str | None = None`. Make it a
   required `str`. Update every test fixture that omits it and the demo `registry.yaml` if any
   entry lacks it (none did at review time). Add a test that a tool without `owner` is rejected
   (`test_invalid_entries_are_rejected` in `test_registry.py` is the place). Mention it in the
   note's "Control plane and data plane" section.

4. Undeclared dependencies. `gateway/__main__.py` imports `anyio` and `gateway/policies.py`
   imports `mcp_types`, and `packages/mcp-gateway/pyproject.toml` declares neither. Add
   `anyio==4.15.1` and `mcp-types==2.3.0` to the gateway's `dependencies` (those are the versions
   `uv.lock` already resolves), run `uv lock`, and commit the lock change. `uv sync --locked` must
   still pass.

5. Two gaps the note does not state. Add to the "Known gaps" list in `docs/notes/m2a.md`:
   rate limits cover tool calls only, so resource reads and prompt gets are unlimited (the
   middleware docstring in `gateway/policies.py` already says "executed tool calls"); and the
   `stdio` source's `command` runs in the gateway's working directory, so the demo registry's
   `uv run opsdesk-server` works only when `mcp-gateway serve` starts from the repository root,
   while a relative `spec:` path is resolved against the registry's directory. Also say so in the
   comment at the top of `packages/mcp-gateway/registry.yaml`. Do not change the command itself.

Report: commits, the `scripts/check.sh` result, which new tests you ran against `71d9f00` and how
they failed there, the route taken for finding 1, and the exact lines `mcp-gateway audit` now
prints for the demo registry (Task 3 updates the README from them).

### Task 2: OpsDesk: list results carry cache hints, the read-only hints are pinned, the plans carry corrections

Findings this task fixes, each with how it was shown:

1. `resources/list` carries no cache hint. `docs/notes/m1.md` line 21 says "list/read results
   carry `ttlMs` + `cacheScope` ... OpsDesk lists are `public` / 60s". `CACHE_HINTS` in
   `packages/opsdesk-server/src/opsdesk/server.py` covers `tools/list`, `prompts/list`,
   `resources/templates/list` and `resources/read`, and `resources/list` answered `ttlMs 0, private`
   at runtime.

   Fix: add `"resources/list": CacheHint(ttl_ms=60_000, scope="public")` to `CACHE_HINTS`. Add or
   extend a test in `packages/opsdesk-server/tests/test_tools.py` or `test_resources.py` that
   iterates over every list method OpsDesk serves (`tools/list`, `prompts/list`, `resources/list`,
   `resources/templates/list`) and asserts each result's hint is `ttlMs 60000` and scope `public`,
   so a method added later without a hint fails the test. Name the test in `docs/notes/m1.md`
   next to the caching claim.

2. No test pins `readOnlyHint` on `list_incidents`. The README lists `readOnlyHint` for
   `list_incidents` and `get_service_status`; only `get_service_status` is asserted
   (`test_tools.py` line 27). A mutation that dropped the hint from `list_incidents` left every
   suite green.

   Fix: parametrize the annotation assertions over every tool: `list_incidents`,
   `get_service_status` and `run_diagnostics` are `readOnlyHint: true` and not destructive;
   `restart_service` and `update_runbook` are `destructiveHint: true` and not read-only;
   `restart_service` is `idempotentHint: false` and `update_runbook` `idempotentHint: true`. Every
   tool has `openWorldHint: false`. Show in the report that reverting the `list_incidents` hint
   fails the new test.

3. The plans are out of date in two places. `docs/superpowers/plans/2026-10-12-m1-opsdesk-server.md`
   line 34 lists `-32603 | Generic ResourceError` under error codes "asserted in tests"; no test
   asserts -32603 and no OpsDesk code path raises it. `docs/superpowers/plans/2026-10-14-m2a-gateway-core.md`
   line 12 says the limiter "counts only the first MRTR round" and line 36 says "Count only calls
   without `request_state`"; the code reserves a slot on every round and refunds only on
   `input_required`, as `docs/notes/m2a.md` explains under "Rate limits and MRTR rounds".

   Fix: plans are historical, so do not rewrite the original text. Add a short
   `## Corrections (2026-10-29)` section at the end of each plan stating what the code does
   instead and pointing to the note section that explains why. Two or three sentences each.

4. `docs/notes/m1.md` line 41 says "`ResourceNotFoundError` → -32602, generic `ResourceError`
   → -32603" under gotchas. The first half is tested; the second is not. Either add a focused test
   that a tool-free `MCPServer` resource raising `ResourceError` answers -32603 (acceptable if it
   stays small and uses the in-memory client), or reword the gotcha to say the -32603 mapping is
   from the SDK source and untested here. Say which you did.

Report: commits, the `scripts/check.sh` result, and which new tests you ran against `71d9f00` and
how they failed there.

### Task 3: CI and scripts: the safety nets do what their comments say, a freshness check exists, the README matches

This task starts from the integration branch after Tasks 1 and 2 are merged. Findings, each with
how it was shown:

1. `scripts/check.sh` lines 2 to 4 overstate `-X dev`. They say asyncio debug mode "catches
   thread-safety and slow-callback problems". A scratch test that blocked the event loop for 300 ms
   under `-X dev` with warnings as errors passed: the slow-callback report is a log line and never
   fails a test. Rewrite the comment to what the flag does here: it enables asyncio debug mode,
   which turns un-awaited coroutines and unclosed resources into warnings that `filterwarnings =
   error` fails, and logs (only logs) slow callbacks.

2. The ascii-locale CI job does less than its comment says. `.github/workflows/ci.yml` lines
   22 to 24 say "a file read or written without an explicit encoding fails here". Under `LC_ALL=C
   PYTHONUTF8=0`, a read or write of ASCII data without `encoding=` passes; only non-ASCII data
   fails. There are 41 `read_text`, `write_text` and `open` calls without `encoding=` in the test
   files (for example `packages/mcp-gateway/tests/conftest.py` line 46). The `src/` trees are
   clean.

   Fix: add `-X warn_default_encoding` to the python invocation in `scripts/check.sh` (it raises
   `EncodingWarning` for every text open without an explicit encoding, and `filterwarnings = error`
   turns that into a failure in every CI job and locally). Then add `encoding="utf-8"` to every
   such call in `tests/` and `packages/*/tests/` until the check is green. Correct the ci.yml
   comment so it describes the two mechanisms accurately.

3. CI cancels in-progress runs on `main`. `concurrency.cancel-in-progress: true` applies to
   every ref, and the run for the merge of PR #5 on `main` was cancelled when PR #6 landed a few
   seconds later, so that merge commit never had a complete run. Change it to
   `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.

4. No monthly freshness check. The design spec's rules say: "A monthly freshness check flags
   new releases of the spec, `mcp`, `fastmcp`, `a2a-sdk` and the conformance tooling." Nothing in
   the repository does this.

   Fix: add `.github/dependabot.yml` with monthly updates for the `uv` ecosystem (the root
   `pyproject.toml` and lock) and for `github-actions`. Add `scripts/freshness.sh`, which compares
   the pinned versions with the latest published ones and exits 1, printing one line per stale pin,
   when any is behind: `mcp` and `fastmcp` from `uv.lock` against PyPI (`uv pip index versions` or
   the PyPI JSON API), `@modelcontextprotocol/conformance` and `@modelcontextprotocol/inspector`
   from `scripts/conformance.sh` and `scripts/inspector-smoke.sh` against `npm view`, and the MCP
   spec against the latest tag or release of `github.com/modelcontextprotocol/modelcontextprotocol`
   compared with the `2026-07-28` date the README names. Skip `a2a-sdk` until M4 pins it, and say
   so in a comment. Add `.github/workflows/freshness.yml` that runs it on a monthly `schedule` and
   on `workflow_dispatch`. Run the script locally once and put its output in the report; if it
   reports stale pins today, that is the expected result, not something to fix in this task.

5. Two CI pins float. `astral-sh/setup-uv@v10.3.0` has no `version:` input, so the uv version
   floats. `node-version: "22"` floats the minor and patch. Pin `setup-uv` to the uv version the
   checkout uses (`uv --version`). For Node, pin an exact version that you confirm exists (for
   example with `npm view node@22 version` or the nodejs.org release index); if you cannot confirm
   one, leave it and say so.

6. `scripts/review-package.sh` line 34 exits silently with no merge base. With two refs that
   share no history (an orphan branch, a shallow clone), `git merge-base --all | wc -l` fails under
   `pipefail` and the script exits 1 with no message and no file. Detect it and exit 2 with a
   message naming both refs. A test exists for this script in `tests/test_review_package.py`; add a
   case.

7. `scripts/conformance.sh` lines 26 to 32 wait for `nc -z` on the fixed port 18765 and never
   check that `$SERVER_PID` is alive, so a stray process on that port would be tested instead of
   OpsDesk, and a server that died at startup would wait the full 10 seconds. Check `kill -0
   "$SERVER_PID"` inside the loop and fail fast with a message if it has exited.

8. shellcheck. No script is linted. Add a CI step `shellcheck scripts/*.sh` to the `python`
   job (GitHub's Ubuntu runners ship shellcheck). Run it locally if `shellcheck` is installed and
   fix what it reports; if it is not installed, say so in the report so the first CI run is watched.

9. README. Line 113 says "`./scripts/check.sh` runs what CI runs"; CI's `protocol` job also
   runs `conformance.sh` and `inspector-smoke.sh`. Reword. Add one sentence to the Gateway section
   saying `mcp-gateway serve` must run from the repository root because the demo registry's
   `stdio` command is `uv run opsdesk-server`. Update the sample `mcp-gateway audit` output block
   to the exact lines Task 1 made it print (given in the dispatch). Add the freshness check to the
   "Test pyramid" table or a sentence under it.

Branch protection on `main` is a repository setting, not a file, so it is not part of this task.
